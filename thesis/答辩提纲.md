# 毕业答辩提纲

## 一、建议演示顺序（8~10 分钟）

1. **课题背景**：小型网络设备增多，人工巡检效率低，大型网管平台复杂。
2. **系统目标**：轻量级、可解释、可扩展的设备监测与告警系统。
3. **技术架构**：Spring Boot 4 + MySQL + Thymeleaf + Bootstrap + ECharts；Ping + SNMP。
4. **设备管理**：新增、编辑、删除、IPv4 校验、重复 IP 校验、搜索分页。
5. **Ping 监测**：单台/全部/定时，响应时间解析，监测历史。
6. **告警规则**：连续 3 次离线、响应时间 100ms、告警去重、确认、恢复。
7. **数据看板**：设备状态、24 小时趋势、告警分布。
8. **SNMP 扩展**：sysName/sysDescr/sysUpTime，模拟 Agent，社区字符串保护。
9. **测试结果**：23 个自动化测试、超时数据、MySQL 503/200、移动端适配。
10. **不足与展望**：无登录权限、SNMP v2c 限制、真实设备验证不足、后续扩展。

## 二、现场演示路线

1. 打开首页，说明当前阶段和技术栈。
2. 进入设备管理，展示 4 台设备、搜索、分页。
3. 打开设备 3 详情，点击“立即检测”，查看响应时间和监测历史。
4. 点击“SNMP 采集”，展示 sysName、sysDescr、sysUpTime。
5. 进入告警中心，展示已确认离线告警和已恢复延迟告警，演示筛选。
6. 进入数据看板，展示汇总、趋势、设备分布、告警分布。
7. 说明 MySQL 断连时健康检查 503、恢复后 200 的测试结果。

## 三、答辩重点

### 1. 为什么不用 Java 原生 ICMP？

Windows 下原生 ICMP Socket 通常需要管理员权限，普通用户运行会失败。调用系统 `ping.exe` 更稳定，也便于在本科环境中部署；程序解析中英文输出并记录响应时间。

### 2. 为什么用连续失败而不是一次失败就告警？

一次丢包可能是瞬时拥塞或 ICMP 限速，直接告警容易误报。连续 3 次失败才触发 CRITICAL，降低误报；阈值可以通过配置调整。

### 3. 告警去重怎么实现？

同一设备、同一告警类型在 OPEN/ACKNOWLEDGED 期间只保留一条活动告警。持续异常时增加 `occurrence_count` 和 `last_seen_at`，恢复时把原记录改为 RECOVERED，而不是插入新记录。

### 4. 社区字符串怎么保护？

社区字符串只保存在数据库；API 只返回 `snmpCommunityConfigured` 布尔值；页面编辑不回显；日志不打印。模拟 Agent 使用测试值 `sim-public`，不是真实密码。

### 5. 数据库断连怎么验证？

在管理员 PowerShell 中停止 MySQL84，`/api/health` 返回 503；重新启动后恢复 200，设备 API 和数据库查询正常，Hikari 自动重连，应用无需重启。

### 6. 系统有什么不足？

没有登录权限；SNMP 只支持 v2c，社区字符串是数据库明文存储；没有真实交换机/路由器验证；没有邮件/短信通知；大规模并发和长时间稳定性尚未测试。

### 7. 创新点/特点怎么说？

不要夸大“创新”。可以强调：

- 面向中小型网络的轻量级实现；
- Ping + SNMP + 告警 + 看板的一体化；
- 告警去重、确认和恢复状态机；
- 阈值配置化、分层清晰、可测试；
- 本地 ECharts，不依赖 CDN；
- 真实测试数据完整记录。

## 四、常见追问

| 问题 | 回答要点 |
|---|---|
| 为什么不用 Vue/React？ | 毕设目标是轻量级单体系统，Thymeleaf 足够，减少构建和部署复杂度。 |
| 为什么用 JPA 而不是 MyBatis？ | 实体关系简单，JPA 减少重复 SQL；复杂查询用 `@Query`，表结构仍由 SQL 显式维护。 |
| 告警会不会重复爆炸？ | 有活动告警去重，同一设备同一类型只保留一条；持续异常只增加次数。 |
| 如何避免把没有检测画成 0ms？ | 趋势接口对空时间桶返回 `null`，ECharts 显示断点。 |
| 为什么 SNMP 端口用 1161？ | 本机模拟 Agent 使用非特权端口，便于普通用户测试；真实设备通常使用 161。 |
| 系统能监测多少设备？ | 当前是顺序检测，4 台设备约 1.94 秒；大规模需要异步和批量优化，论文中已说明。 |
