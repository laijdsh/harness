# 数据库设计说明

更新时间：2026-11-26  
当前阶段：阶段 6（SNMP v2c 扩展）

## 1. 设计目标

数据库需要同时支持：

1. 网络设备基础资料维护。
2. 每次 Ping 检测历史保存。
3. 设备当前状态和“最近一次检测摘要”快速展示。
4. 告警记录、告警确认和恢复状态查询。
5. 后续趋势图查询。

设计原则：

1. 表结构由 `sql/init.sql` 显式创建，JPA 只做 `validate`，避免自动改表。
2. 设备 IP 必须唯一，从数据库层面防止重复登记。
3. 设备类型和状态使用字符串枚举，便于 SQL 查看。
4. 高频查询字段建立索引。
5. 时间字段使用 `DATETIME(6)`，保留毫秒/微秒精度。
6. 不在数据库脚本中保存任何密码。

## 2. E-R 关系说明

当前已实现：

```text
network_device（设备）
    │
    ├── 1 : N ── monitor_record（监测记录）
    │
    └── 1 : N ── alert_record（告警记录）
```

关系说明：

- 一台设备可以有多条监测记录。
- 一台设备可以有多条告警记录，但同一设备、同一告警类型在未恢复期间
  只保留一个活动告警，由 Service 层保证。
- `monitor_record.device_id` 和 `alert_record.device_id` 都外键关联
  `network_device.id`。
- 删除设备时，监测记录和告警记录通过 `ON DELETE CASCADE` 级联删除。
- 如果后续实现登录，再增加 `sys_user` 表，本阶段不引入。

## 3. network_device 设备信息表

### 3.1 字段设计

| 字段 | 类型 | 允许空 | 键/默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | 主键，自增 | 设备主键 |
| `device_name` | VARCHAR(100) | 否 | 普通索引 | 设备名称 |
| `ip_address` | VARCHAR(45) | 否 | 唯一索引 | 设备 IP，字段预留 IPv6 长度 |
| `device_type` | VARCHAR(20) | 否 | 普通索引 | 设备类型 |
| `area` | VARCHAR(100) | 是 | — | 所属区域 |
| `description` | VARCHAR(255) | 是 | — | 备注 |
| `status` | VARCHAR(20) | 否 | 默认 `UNKNOWN`，普通索引 | 当前监测状态 |
| `last_checked_at` | DATETIME(6) | 是 | 普通索引 | 最近一次检测时间 |
| `last_response_time_ms` | INT | 是 | — | 最近一次响应时间（毫秒） |
| `snmp_enabled` | TINYINT(1) | 否 | 默认 0 | 是否启用 SNMP |
| `snmp_version` | VARCHAR(10) | 否 | 默认 `2c` | SNMP 版本，当前仅 2c |
| `snmp_port` | INT | 否 | 默认 161 | SNMP UDP 端口 |
| `snmp_community` | VARCHAR(100) | 是 | — | 社区字符串，敏感字段 |
| `snmp_status` | VARCHAR(20) | 否 | 默认 `DISABLED`，普通索引 | DISABLED/OK/UNREACHABLE/ERROR |
| `snmp_sys_name` | VARCHAR(255) | 是 | — | sysName |
| `snmp_sys_descr` | VARCHAR(500) | 是 | — | sysDescr |
| `snmp_sys_uptime_ticks` | BIGINT | 是 | — | sysUpTime，1/100 秒 |
| `snmp_last_checked_at` | DATETIME(6) | 是 | — | 最近一次 SNMP 采集时间 |
| `snmp_message` | VARCHAR(255) | 是 | — | 最近一次 SNMP 采集说明 |
| `created_at` | DATETIME(6) | 否 | 普通索引 | 创建时间 |
| `updated_at` | DATETIME(6) | 否 | — | 最后更新时间 |

`last_checked_at` 和 `last_response_time_ms` 是“最近一次摘要”，用于设备列表快速展示；
完整历史仍在 `monitor_record` 中。

### 3.2 枚举取值

设备类型 `device_type`：

| 值 | 页面名称 |
|---|---|
| `ROUTER` | 路由器 |
| `SWITCH` | 交换机 |
| `SERVER` | 服务器 |
| `OTHER` | 其他设备 |

设备状态 `status`：

| 值 | 页面名称 | 说明 |
|---|---|---|
| `ONLINE` | 在线 | 本次 Ping 收到 ICMP 回复 |
| `OFFLINE` | 离线 | 本次 Ping 超时或目标不可达 |
| `UNKNOWN` | 未知 | 新设备，尚未检测 |
| `ERROR` | 检测异常 | Ping 命令执行失败、本机网络异常等 |

注意：`OFFLINE` 表示“本次没有收到 ICMP 回复”，不等于设备一定损坏；防火墙可能屏蔽 ICMP。

### 3.3 主键、索引与约束

```sql
PRIMARY KEY (id)
UNIQUE KEY uk_network_device_ip (ip_address)
KEY idx_network_device_name (device_name)
KEY idx_network_device_type (device_type)
KEY idx_network_device_status (status)
KEY idx_network_device_last_checked_at (last_checked_at)
KEY idx_network_device_snmp_status (snmp_status)
KEY idx_network_device_created_at (created_at)
CONSTRAINT chk_network_device_type
    CHECK (device_type IN ('ROUTER', 'SWITCH', 'SERVER', 'OTHER'))
CONSTRAINT chk_network_device_status
    CHECK (status IN ('ONLINE', 'OFFLINE', 'UNKNOWN', 'ERROR'))
CONSTRAINT chk_network_device_snmp_version
    CHECK (snmp_version IN ('2c'))
CONSTRAINT chk_network_device_snmp_status
    CHECK (snmp_status IN ('DISABLED', 'OK', 'UNREACHABLE', 'ERROR'))
```

索引理由：

- `ip_address` 唯一索引：防止重复登记。
- `device_name`：名称模糊搜索。
- `device_type`：类型筛选。
- `status`：首页在线/离线统计。
- `last_checked_at`：最近检测排序或统计。
- `created_at`：设备列表默认排序。

## 4. monitor_record 监测记录表

### 4.1 字段设计

| 字段 | 类型 | 允许空 | 键/默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | 主键，自增 | 记录主键 |
| `device_id` | BIGINT | 否 | 外键，普通索引 | 设备 ID |
| `check_time` | DATETIME(6) | 否 | 普通索引 | 检测时间 |
| `reachable` | TINYINT(1) | 否 | — | 是否收到 ICMP 回复 |
| `response_time_ms` | INT | 是 | — | 响应时间（毫秒），失败为空 |
| `status` | VARCHAR(20) | 否 | 普通索引 | ONLINE/OFFLINE/ERROR |
| `result_message` | VARCHAR(255) | 是 | — | 检测说明或错误原因 |

### 4.2 主键、索引与外键

```sql
PRIMARY KEY (id)
KEY idx_monitor_record_device_time (device_id, check_time)
KEY idx_monitor_record_check_time (check_time)
KEY idx_monitor_record_status (status)
CONSTRAINT fk_monitor_record_device
    FOREIGN KEY (device_id) REFERENCES network_device (id)
    ON DELETE CASCADE
CONSTRAINT chk_monitor_record_status
    CHECK (status IN ('ONLINE', 'OFFLINE', 'ERROR'))
```

设计理由：

- `(device_id, check_time)` 复合索引支持“某台设备按时间倒序查历史”。
- `check_time` 支持全局历史查询和时间范围统计。
- `status` 为后续告警统计和看板准备。
- 外键保证记录不会指向不存在的设备。
- 级联删除表示设备删除后其监测历史一并清理；如果后续论文需要保留审计历史，
  可以改成逻辑删除或 `ON DELETE SET NULL`。

## 6. 数据完整性

| 规则 | 应用层 | 数据库层 |
|---|---|---|
| 设备名称必填 | `@NotBlank` | `NOT NULL` |
| IP 必填且格式正确 | `@NotBlank` + IPv4 `@Pattern` | `NOT NULL` |
| IP 唯一 | Service 重复检查 | `uk_network_device_ip` |
| 设备类型合法 | 枚举 + `@NotNull` | CHECK 约束 |
| 设备状态合法 | 枚举 | CHECK 约束 |
| 记录状态合法 | `DeviceStatus` 枚举 | CHECK 约束 |
| 记录必须属于设备 | Service 只使用已有设备 ID | 外键 `fk_monitor_record_device` |
| 检测时间必填 | Service 赋值 | `NOT NULL` |
| 告警类型/级别/状态合法 | Java 枚举 | CHECK 约束 |
| 告警必须属于设备 | Service 只使用已有设备 ID | 外键 `fk_alert_record_device` |
| 活动告警去重 | AlertService 查询同一设备同一类型 | 无数据库唯一约束 |
| 告警时间必填 | AlertService 赋值 | `triggered_at`、`last_seen_at` NOT NULL |
| SNMP 版本合法 | Service 固定为 2c | CHECK 约束 |
| SNMP 状态合法 | SnmpStatus 枚举 | CHECK 约束 |
| 社区字符串保护 | API/DTO 不返回、日志不打印 | 字段可为 NULL |

## 8. alert_record 告警记录表

### 8.1 字段设计

| 字段 | 类型 | 允许空 | 键/默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | 主键，自增 | 告警主键 |
| `device_id` | BIGINT | 否 | 外键，普通索引 | 设备 ID |
| `alert_type` | VARCHAR(30) | 否 | 普通索引 | DEVICE_OFFLINE/HIGH_LATENCY |
| `alert_level` | VARCHAR(20) | 否 | — | INFO/WARNING/CRITICAL |
| `message` | VARCHAR(255) | 否 | — | 告警内容 |
| `status` | VARCHAR(20) | 否 | 默认 OPEN，普通索引 | OPEN/ACKNOWLEDGED/RECOVERED |
| `triggered_at` | DATETIME(6) | 否 | 普通索引 | 首次触发时间 |
| `last_seen_at` | DATETIME(6) | 否 | — | 最近一次仍然异常的时间 |
| `recovered_at` | DATETIME(6) | 是 | — | 恢复时间 |
| `acknowledged_at` | DATETIME(6) | 是 | — | 确认时间 |
| `occurrence_count` | INT | 否 | 默认 1 | 持续出现次数 |

### 8.2 枚举取值

告警类型 `alert_type`：

| 值 | 页面名称 | 触发规则 |
|---|---|---|
| `DEVICE_OFFLINE` | 设备离线 | 连续 N 次 OFFLINE |
| `HIGH_LATENCY` | 响应延迟 | 在线且响应时间超过阈值 |

告警级别 `alert_level`：

| 值 | 页面名称 |
|---|---|
| `INFO` | 提示 |
| `WARNING` | 警告 |
| `CRITICAL` | 严重 |

告警状态 `status`：

| 值 | 页面名称 | 说明 |
|---|---|---|
| `OPEN` | 未恢复 | 异常仍然存在 |
| `ACKNOWLEDGED` | 已确认 | 管理员已确认，但异常可能仍存在 |
| `RECOVERED` | 已恢复 | 设备/延迟已恢复正常 |

### 8.3 主键、索引与外键

```sql
PRIMARY KEY (id)
KEY idx_alert_device_triggered (device_id, triggered_at)
KEY idx_alert_triggered_at (triggered_at)
KEY idx_alert_status (status)
KEY idx_alert_type_status (alert_type, status)
CONSTRAINT fk_alert_record_device
    FOREIGN KEY (device_id) REFERENCES network_device (id)
    ON DELETE CASCADE
CONSTRAINT chk_alert_record_type
    CHECK (alert_type IN ('DEVICE_OFFLINE', 'HIGH_LATENCY'))
CONSTRAINT chk_alert_record_level
    CHECK (alert_level IN ('INFO', 'WARNING', 'CRITICAL'))
CONSTRAINT chk_alert_record_status
    CHECK (status IN ('OPEN', 'ACKNOWLEDGED', 'RECOVERED'))
```

索引理由：

- `(device_id, triggered_at)`：按设备检索告警历史。
- `triggered_at`：告警列表按时间倒序。
- `status`：筛选未恢复/已确认/已恢复。
- `(alert_type, status)`：按类型加载活动告警，实现去重。

### 8.4 告警去重设计

MySQL 没有跨行的部分唯一索引，因此活动告警去重由 `AlertService` 完成：

1. 查询同一 `device_id`、`alert_type`，状态为 `OPEN` 或 `ACKNOWLEDGED` 的最新记录。
2. 存在活动告警时只更新 `last_seen_at`、`occurrence_count` 和内容。
3. 不存在时才插入新告警。
4. 恢复时把原记录改为 `RECOVERED`，而不是新增一条恢复记录。

这样既保留完整历史，又避免持续异常每分钟产生一条重复告警。

## 10. 阶段 5 数据聚合说明

阶段 5 没有修改表结构，看板数据全部从现有表实时聚合：

| 数据 | 来源 | 方式 |
|---|---|---|
| 设备总数/在线/离线 | `network_device.status` | `countByStatus` |
| 未恢复告警 | `alert_record.status` | OPEN + ACKNOWLEDGED 计数 |
| 监测记录总数 | `monitor_record` | `count()` |
| 响应时间趋势 | `monitor_record.check_time/response_time_ms` | 按时间桶平均 |
| 告警分布 | `alert_record.alert_type/level/status` | 内存分组统计 |

响应时间趋势使用 `idx_monitor_record_check_time` 支撑时间范围查询。
当前数据量约 1300 条，Java 层聚合足够；如果后续数据量明显增大，可以改成
MySQL `GROUP BY` 聚合查询或增加预聚合表。

## 11. 阶段 6 SNMP 字段说明

阶段 6 在 `network_device` 上增加 SNMP 配置和最近一次采集结果，不新增独立表。

### 11.1 OID

| 字段 | OID | 类型 |
|---|---|---|
| sysDescr | `1.3.6.1.2.1.1.1.0` | OCTET STRING |
| sysUpTime | `1.3.6.1.2.1.1.3.0` | TimeTicks |
| sysName | `1.3.6.1.2.1.1.5.0` | OCTET STRING |

### 11.2 状态

| 值 | 页面名称 | 说明 |
|---|---|---|
| `DISABLED` | 未启用 | 设备未开启 SNMP |
| `OK` | 正常 | 最近一次采集成功 |
| `UNREACHABLE` | 不可达 | 超时、端口关闭或社区字符串错误 |
| `ERROR` | 采集异常 | 解析、网络或程序异常 |

页面还会在“已启用但从未采集”时显示“未检测”，该状态由 DTO 根据
`snmp_last_checked_at IS NULL` 推导，不额外写入数据库。

### 11.3 安全设计

- `snmp_community` 只供 `SnmpService` 读取，不进入 `DeviceResponse`。
- 页面表单编辑时不回显社区字符串，留空表示保留原值。
- 日志只记录设备 IP 和采集状态，不记录社区字符串。
- 模拟 Agent 使用测试社区字符串 `sim-public`，不是实际设备密码。
- 真实部署时应限制数据库访问权限，后续可扩展为加密存储或外部密钥管理。
